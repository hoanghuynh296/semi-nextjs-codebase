# Semi Design System — Decision Log

Newest first. Each entry is a user decision already reflected in `DESIGN_SYSTEM.md`, `QUICK_REF.md` and `lint/semi-lint.mjs`.

- **2026-11-01 (v0.13.3):** The design system pages describe the system, not a set of options: the docs show the styles only, and the foundations page is generated from `tokens/` like the component pages are generated from `examples/`. A page that repeats values by hand is a page that goes wrong after the next token change.
- **2026-11-01 (v0.13.2):** Surfaces of a tinted brand stay almost neutral. A hue on large backgrounds is what people perceive as a colour cast, while the hue is still useful on text and borders, so the two get separate chroma values. Values follow common practice: Tailwind slate-50 ≈ 0.003, Radix slate-1 ≈ 0.002, shadcn Neutral 0 (measured from published hex values, not an official standard).
- **2026-11-01 (v0.13.0):** Agents ask the docs instead of reading files: one small core (`cli/core.mjs`) serves both a CLI and an MCP server, both shipped inside `@semi/ui` so answers always match the installed version; the plugin only launches the project's copy. No MCP SDK or search library: newline JSON-RPC and a weighted keyword search (Vietnamese UI terms → English, IDF, the docs' own *use something else when* rows as redirects) are enough for ~130 docs and keep zero dependencies. Blocks are ordinary docs (group Blocks) so the site, the markdown, search and `semi add` need no second system.
- **2026-11-01 (v0.12.0):** Agent UIs show what the agent did, in order, inside the chat: reasoning, plan, tool calls, approvals, output and sources are separate parts, not one generic “step” component, because agents (and people) need to pick the right one by meaning. Every outward-facing, paid or irreversible agent action goes through `ActionConfirmation`, and the decision stays visible in the log. Details sit behind disclosures and are never live regions, so a screen reader hears the answer, not every token or log line. Change marks and statuses are text first and colour second (amber text misses AA on light surfaces, so colour moves to a dot).
- **2026-11-01 (v0.11.0):** Charts are drawn in SVG by `@semi/ui`, no chart library: a small fixed set (bar, line, donut, sparkline) that follows the dataviz method instead of a general plotting API. Series colours are eight `chart-*` tokens in a fixed order, checked for colour-blind separation in both themes, so a series keeps its colour when filters change and a ninth series folds into “Khác”; there is never a second y axis. Every chart has a keyboard tooltip and a table view, so colour and hover are never the only way to read it. `NavigationMenu` (website links, disclosure buttons) and `Menubar` (tool commands, ARIA menubar) stay separate because they are different patterns for assistive tech.
- **2026-11-01 (v0.10.0):** The missing building blocks (shadcn-level coverage) are written in-house, on Semi tokens, with no runtime dependency: Command, Calendar, DataTable, Slider and the floating layers reuse Semi's own positioning and focus code. Search everywhere (Command, DataTable) ignores Vietnamese marks, because people type without them. DatePicker now uses Calendar so there is one date grid with full keyboard support. A Sheet is `Drawer side="top|bottom|left|right"`, not a second component.
- **2026-11-01 (v0.9.0):** Docs agent first, shadcn-like but in Semi's own look, no external libraries. One source per component (`examples/<id>/meta.json` + example files) feeds the docs site, the agent markdown and the brand previews, and the API tables come from the TypeScript types, so docs cannot drift from code. The fields agents need most are `when` and `instead` (which component, and what to use otherwise); every example is a real file that type-checks and imports from `@semi/ui` only, so copying it is safe. The Storybook pages are replaced by the docs site; brand kits render the same pages so a brand sees every component in its colours.
- **2026-11-01 (v0.7.0):** Semi is a multi-brand kit (core for subsidiaries and clients; 3D Noobs is the first brand). No designer in the loop, so the kit holds templates (styles, palettes) and rules, and each brand customises inside them: three layers, Semi core → brand kit (one repo per brand, never inside the core repo) → products that only install the kit. A brand decides only what a brand designer would choose independently (primary, optional secondary, neutral mood, allowed styles, fonts); everything derivable (scales, theme shades, on-colours, neutrals per style) is generated in OKLCH with the first shades that reach AA. Products cannot drift: `brand-override`, the audit's brand check, styles limited to the brand's list. A brand may allow several styles (a tool on Flat, a store on Soft, same colours and fonts). Updates flow top-down: `/semi-brand update` in the kit for a new Semi, `/semi-update` in products (major brand changes are asked first; the kit's `"semi"` range keeps products on a compatible Semi).
- **2026-11-01 (v0.7.0):** Palettes. Sharp's pure black and white was too harsh as the only option, and teams want another colour mood without leaving a style. Each style now has three palettes: variants of the neutral colours only (both themes), so the accent stays the product's brand and status colours keep their meaning; the first palette is the default and needs no attribute. Sharp defaults to Ink (off-black / off-white), keeping pure black and white as Mono. Every style × palette × theme is contrast-checked on every Storybook page.
- **2026-11-01 (v0.7.0):** Styles carry the look, not only the shape. Radii and a shadow alone did not make Soft or Sharp read as different, so a style also sets the neutral colours of both themes, the fonts, the card border and control sizes (the biggest visual levers). Still shared: components, layout, type scale, the accent (it is the product's brand, §2b, so two apps on the same style keep their own colour) and status / tone colours (meaning). Layout stays out of styles: it follows the kind of app (AppShell, AppHeader, later other shells usable in every style), and a style switch must never need code changes. Every style × theme is contrast-checked on every Storybook page.
- **2026-11-01 (v0.7.0):** Styles. Apps should be able to pick a look (Flat today, Soft now, more later) without a second component set: one set of components with N sets of shape tokens, because a forked set would need every fix N times and agents would mix them up. A style changes only radii and the resting card shadow; colours (they carry meaning and contrast), type, spacing, layout and the component API are shared, so contrast and a11y hold in every style. Radii became semantic tokens (`rounded-chip|control|card|panel`) read through `--semi-*` variables, so a `[data-style]` scope re-styles its subtree (Storybook previews) and Flat stays pixel-identical. An app sets the style in one place (`<html data-style>`, mirrored in `semi-lint.json` for the audit), not as a user preference like the theme. Raw radii are ratchet debt (`radius-token`) that the codemod maps, so existing apps follow the style after `/semi-fix`. Changing an existing app's style is its own job (`/semi-style`).
- **2026-11-01 (v0.7.0):** One command per job, modelled on Storybook (`init` / `doctor` / `automigrate` / `upgrade`) and Nx (`migrate` writes a plan file, then runs it). `/semi-init` only creates new apps. An existing app — with or without `@semi/ui` — goes `/semi-audit` → `/semi-fix`, and installing Semi is the fix's first phase (foundation), so there is never an installed-but-unstyled gap and every visible change goes through one reviewed place (screenshots before / after, `defaultTheme` kept). Phases (foundation → tokens → hand fixes → structure) each leave the app building. The audit hands its work over in `semi-audit.md`, refreshed when the code changed and deleted once clean. Structural choices the team keeps live in `semi-lint.json` `keep`. `/semi-update` only upgrades, but runs the migrations a release ships for its own breaking changes (like `ng update`), never a general audit.
- **2026-10-31 (v0.7.0):** Docs and code stay in sync by check, not by memory: `check:manifest` fails on usage snippets that import missing exports, Storybook sections without usage (or the reverse), and components / hooks missing from `DESIGN_SYSTEM.md`. What a regex cannot check (prose matching behaviour) is listed in the `AGENTS.md` change checklist. `CLAUDE.md` imports `AGENTS.md` so Claude Code maintainers read it too.
- **2026-10-31 (v0.6.0 / AI chat):**
  - *Context:* AI panels are used in most Semi apps, and §14 said each app kept its own chat parts. 3D Noobs Studio (`web-slicer`) had a good structure (shared shell, list, composer, suggestion rows used by four features), but it could not be reused as-is: dark-only colours (`text-white`, `gray-*`, `white/[0.05]`, `amber/rose-*`), px text sizes, hard-coded Vietnamese strings, app types (AI profiles / settings) inside the parts, a list that always jumped to the bottom, and no screen-reader handling of streamed text.
  - *Decision:* The chat moves into `@semi/ui` as `Chat.tsx`, rebuilt on tokens with the Studio look and behaviour kept (side panel, resizable width, keyboard inset, IME-safe Enter, focus return). UI only: messages, streaming, model choice and settings stay in the app (the model picker is a `toolbar` slot). Added: stick-to-bottom only while at the bottom + "jump to latest", one announcement per finished answer, retry, copy, keyboard-resizable edge, `"screen"` placement as a real dialog over a `Modal`. Locale strings `chat*`, `copy`, `copied`. Storybook "AI Chat" page + Playwright checks (both themes, IME, scroll, dialog over modal, phones). The model picker is part of the kit (`ChatModelPicker`: provider → model → effort chips, as in Studio); the provider / model lists stay app data.
  - *Decision — Storybook is read by agents too:* every section carries when-to-use + copy-ready code from one data file (`app/usage.ts`), and the export serves `llms.txt` (index + all usage code), `llms-full.txt`, the docs and `components.json` as plain files, so an agent can learn the system from the deployed Storybook without running JavaScript.
- **2026-10-31 (v0.5.0 / Complete design-system foundation):**
  - *Context:* After v0.4.0 the review found the remaining gaps: no type / z-index / elevation / status-surface tokens (sizes were `text-[13px]` strings, layers were `z-[9000]`…`z-[10001]`), missing primitives (Button, form fields, choices, tabs, menu, toast, alert, table, drawer…), weak accessibility (Modal without focus trap, combobox without ARIA, almost no focus ring), hard-coded Vietnamese strings, and colour rules that were regex over lines — every new spelling slipped through (issues #1–#4), and the demo pages hid 13 light-mode contrast failures that lint never saw.
  - *Decision — tokens:* type scale `text-caption`…`text-display` (11–26px) replaces px classes; layers `z-sticky`…`z-tooltip`; `bg-overlay`; `shadow-overlay` / `shadow-float`; status `*-bg` / `*-border` / `*-solid`; easing tokens; radius scale pinned.
  - *Decision — components:* `Button`, `Spinner`, `Field` + `Input` / `Textarea`, `Checkbox`, `Switch`, `RadioGroup`, `Tabs`, `Tooltip`, `Menu`, `toast` + `ToastHost`, `Alert`, `Progress`, `Avatar`, `EmptyState`, `Table`, `Drawer`. Dialog behaviour is shared (`useDialog`: focus trap, scroll lock, Escape, focus return); UI strings come from `SemiLocaleProvider` (vi default, `en` shipped).
  - *Decision — enforcement:* colour / size rules analyse class tokens of every string literal and `@apply` (`lint/classes.mjs`), with variants and every colour prefix; new ratchet rules `no-fixed-tone-text`, `literal-colour-value`, `arbitrary-text-size`; `hex-colour-class` covers any arbitrary colour. The `/semi-init` codemod rewrites tokens inside string literals only, collapses `X dark:Y` pairs, handles dark-first apps, and reports what it cannot map (`--dry-run` report).
  - *Decision — migration:* `/semi-audit --inventory` exports per-file debt by module and a coverage %; `/semi-init` plans Foundation (mandatory) and Patterns (opt-in) tracks, one PR per module, with a Definition of Done of zero findings + both themes checked. A baseline is only a temporary net.
  - *Decision — quality gates:* `npm test` (lint / codemod fixtures), `npm run test:ui` (Playwright: AA contrast on every Storybook page in both themes, axe WCAG 2.1 AA, theme before paint, keyboard flows), `components.json` generated from source and checked in CI.
- **2026-10-31 (v0.4.0 / Phase 0 hardening):**
  - *Context:* A review found that the library itself failed light mode (`text-rose-400`, `text-primary-400`, `text-*-300` were 1.9–2.7:1 on white), `BTN_PRIMARY` was 2.94:1 in both themes (white on `primary-500`), dark `text-muted` was 3.64:1, the theme flashed dark on load for light-mode users (ThemeProvider applied the stored theme only after hydration), and `/semi-audit` ran a stale vendored copy of `semi-lint` (without the Issue #3/#4 fixes).
  - *Decision:* Every text/background pair in shared UI must reach WCAG AA (4.5:1) in both themes, through themed tokens instead of fixed shades or `dark:` pairs: `bg-accent` / `hover:bg-accent-hover` / `text-on-accent` (dark: `primary-500` with near-black text, light: `primary-700` with white), `text-accent-fg`, `text-danger|success|warning|info-fg`, `text-tone-<hue>` for 12 hues. `text-muted` is `#8b919a` dark / `#5b6779` light. Semantic tokens are generated as `--semi-*` sources read through `@theme inline` (no self-referencing `--color-*`).
  - *Theming:* `<ThemeScript />` in `<head>` applies the stored theme before paint; `ThemeProvider` no longer overwrites it on mount; `data-theme="system"` follows the OS in CSS; `<ThemeSwitcher />` is the standard three-way picker and theme-dependent controls stay unselected until `useTheme().mounted`.
  - *Tooling:* `npm run check` now also fails on stale plugin vendor copies (`scripts/sync-vendor.mjs`) and on version drift across manifests (`scripts/bump-version.mjs`); `/semi-audit` takes its literal-palette pattern from `semi-lint`. Added `<Card>` so `card-class-override` targets a real component (any `bg-*` / `shadow-*`). CI runs `check` + build on every PR.

- **2026-10-31 (v0.3.6 / Universal Tonal Theme-Matching Across All Component Types):**
  - *Context:* Tonal colors are not limited to chips or badges. Real-world consumer applications have tonal accents across many component types: Bento Cards, stat widgets, alert banners, callouts, table rows, action buttons, dividers, and rings. Solid pastels (`bg-*-50`, `border-*-200`) glaringly fail in Dark Mode across all these components.
  - *Decision:* Generalized the Theme-Matching Tonal Architecture to apply universally across all component types and interactive states:
    - Added `TONAL_CONTAINER` and `TONAL_HOVER` to `@semi/ui/styles`.
    - Enhanced `/semi-audit` to inspect and report chromatic tonal usage across cards, callouts, banners, rows, buttons, badges, chips, rings, and dividers across 16 chromatic hues.
    - Enhanced `/semi-init` codemod (`runSemanticCodemod`) to automatically adapt all component states: static background (`bg-*-500/10`), hover background (`hover:bg-*-500/15`), active background (`active:bg-*-500/20`), static border (`border-*-500/20`), hover border (`hover:border-*-500/30`), dividers (`divide-*-500/20`), rings (`ring-*-500/20`), and dual-theme high-contrast text (`text-*-700 dark:text-*-300`).
    - Tightened `no-solid-pastel-surfaces` in `semi-lint` to detect hover, active, border, divide, ring, and all 16 Tailwind chromatic hues.
- **2026-10-31 (v0.3.5 / Theme-Matching Tonal Components):**
  - *Context:* Existing projects often feature colored chips/badges (e.g. purple for Pro, amber for Pending). Flat UI migration should not strip these to monotonous gray, but solid pastels (`bg-purple-50`) fail completely in Dark Mode.
  - *Decision:* Standardized Two-Tier Theme-Matching Tonal architecture (`bg-<color>-500/10 border-<color>-500/20 text-<color>-700 dark:text-<color>-300`) across 16 hues. - **2026-10-31 (v0.3.0):** Two-Tier Semantic Tokens & Native Dual-Theme Architecture (`data-theme="dark|light"`).
  - *Context & Problem:* In real-world migrations (e.g. Auton Platform with 60+ legacy screens), wrapping light screens in a dark `AppShell` resulted in a "dark shell, light core" conflict. Hardcoded physical colors (`bg-white`, `text-slate-900`, `border-slate-200`) prevent theme toggling and break design cohesion.
  - *Decision:* Replaced fixed surface color constants with CSS-variable-backed Semantic Tokens (`--color-canvas`, `--color-app`, `--color-panel`, `--color-field`, `--color-raised`, `--color-text-contrast`, `--color-text-body`, `--color-text-muted`, `--color-line`, `--color-line-hover`, `--color-divider`). Tokens switch seamlessly between Dark and Light mode via `[data-theme="dark"]` and `[data-theme="light"]` (or `.dark` / `.light` classes).
  - *Theming Engine:* Added zero-runtime-overhead `ThemeProvider`, `useTheme()`, and `ThemeToggle` to `@semi/ui`. Added standard `sun` and `moon` icons to the icon registry.
  - *Lint Rules:* Added `no-literal-palette` (banning raw `bg-white`, `text-slate-900`, `border-slate-200`, etc. in favor of semantic tokens, tracked via Ratchet baseline) and `card-class-override` (banning background and shadow overrides on `<Card>`). Retired obsolete `input-bg-field` rule because `bg-field` is now the formal semantic background for inputs.
  - *Plugin Automation:* Upgraded `/semi-audit` to report physical class usage and semantic adoption rate. Upgraded `/semi-init` with an automated AST/regex codemod to map legacy Tailwind classes to semantic tokens, and replaced destructive blanket skips (`skip: { ...: ["src/app"] }`) with Ratchet baselines (`semi-lint-baseline.json`).
